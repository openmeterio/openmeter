# Stripe-related error candidates

These are the five remaining Stripe findings from the billing monetary-loss
audit. The numbers retain their original audit IDs. All amounts and provider
identities below are synthetic. This PR preserves regression evidence and
investigation context; it does not change production behavior.

The paid-credit cancellation finding (#3) is tracked by
[PR #5374](https://github.com/openmeterio/openmeter/pull/5374). The legacy unit
conversion finding (#4) is documented separately in
[PR #5375](https://github.com/openmeterio/openmeter/pull/5375).

## Evidence and scope

The tests create and reload invoices through real PostgreSQL-backed billing
services. A deterministic local HTTP transport exercises production Stripe app
code, request encoding, and the Stripe Go v80 SDK. It models distinct invoice
line/item IDs and honors successful-request idempotency keys, including keys
generated by the SDK. It does not contact a live Stripe account.

The discount and split-credit update tests additionally capture behavior at the
existing Stripe client mock boundary. They isolate defects that the earlier
invoice-item ID failure would otherwise prevent from executing. Those tests
are evidence of faulty mappings, not completed incorrect payments.

These are single-invoice provider scenarios, not three-partial-invoice tests.
In #7, two allocations are details of the same invoice. The broader audit's
progressive-invoice cases are outside this PR.

| ID | Candidate | Observed boundary | Monetary interpretation |
| --- | --- | --- | --- |
| #1 | Wrong object IDs during issuing | Persisted invoice becomes `issuing.failed`; no finalization call | Collection blocked; receivable remains |
| #2 | ISK/UGX provider units | Request amount is 100 times too small | Incorrect provider amount; live undercollection unproven |
| #5 | Retrying partial creation repeats items | Provider draft is USD 20 instead of USD 60 | Draft subtotal divergence; final reconciliation could repair it |
| #6 | Discount update corrupts its external ID | Next sync targets one item for both gross and discount | Downstream monetary outcome is masked by #1 |
| #7 | Split-credit allocations share an update target | Two credit deductions target one provider item | Potential missing deduction; execution is masked by #1 |

## #1: Invoice-line IDs are sent to invoice-item endpoints

**Regression:** [finalization_monetary_audit_test.go](../test/app/stripe/finalization_monetary_audit_test.go),
`TestStripeFinalizationMonetaryAudit/TestApprovalPreservesProviderTotalAndReachesFinalization`.

Given a USD 100 service with a USD 40 discount, draft synchronization leaves
OpenMeter with USD 60 due. Approval must synchronize the invoice and finalize
it for payment. Instead, approval persists `issuing.failed`, and the provider
transport records zero finalization calls. This happens both with a clean
initial draft and after partial creation fails and is retried.

The update builders in [appinvoice.go](../openmeter/app/stripe/appinvoice.go)
set request IDs to `stripeLine.ID` (`il_...`).
[UpdateInvoiceLines](../openmeter/app/stripe/client/invoice_line.go) sends those
IDs to `InvoiceItems.Update`, which expects an invoice-item ID (`ii_...`). The
removal list similarly contains line IDs. The transport uses exact item-ID
lookup; it does not make invoice-line IDs work on invoice-item endpoints.

A fix must preserve invoice-line identities where OpenMeter stores external
line references while addressing item endpoints with the underlying item ID
(or deliberately using the appropriate invoice-line API). Check both update
and deletion consumers. Both approval cases should reach finalization with
USD 60 due and no orphaned discount.

Provider contracts: [invoice-line object](https://docs.stripe.com/api/invoice-line-item/object?api-version=2024-06-20),
[update invoice item](https://docs.stripe.com/api/invoiceitems/update?api-version=2024-06-20),
[delete invoice item](https://docs.stripe.com/api/invoiceitems/delete?api-version=2024-06-20).

## #2: ISK and UGX use the wrong provider amount multiplier

**Regression:** [currency_monetary_audit_test.go](../test/app/stripe/currency_monetary_audit_test.go),
`TestStripeInvoicing/TestMonetaryAuditProviderCurrencyUnits`.

For an invoice totaling 500,000 ISK or UGX, Stripe's API representation should
be 50,000,000. The actual request sends 500,000, representing only 5,000 units
of the currency. USD and JPY controls pass. The persisted OpenMeter invoice is
correct; the discrepancy occurs when encoding the provider amount.

[NewStripeCalculator](../openmeter/app/stripe/calculator.go) derives its
multiplier from ISO accounting precision. ISK and UGX have zero accounting
decimal places, but Stripe requires a two-decimal API representation for these
special cases. `RoundToAmount` is shared by ordinary amounts, discounts, and
credits on both creation and update.

The correction belongs in the provider-unit conversion. Preserve accounting
precision, and check every consumer of the provider multiplier. This test
does not establish live acceptance, currency availability for a particular
account, or a completed undercharge.

Provider contract: [Stripe currency special cases](https://docs.stripe.com/currencies#special-cases).

## #5: Partial creation retry duplicates successful invoice items

**Regression:** [invoice_monetary_audit_test.go](../test/app/stripe/invoice_monetary_audit_test.go),
`TestStripeInvoicing/TestMonetaryAuditCreateRetryPreservesProviderTotal`.

For USD 100 gross less a USD 40 discount, the provider accepts the first item
and rejects the second before executing it. Retrying the unchanged invoice
reuses the invoice but creates the successful prefix again. With the current
discount-first ordering, the provider draft becomes `100 - 40 - 40 = 20`,
while OpenMeter still records USD 60.

[CreateInvoice](../openmeter/app/stripe/client/invoice.go) uses a stable invoice
idempotency key. [AddInvoiceLines](../openmeter/app/stripe/client/invoice_line.go)
does not preserve equivalent per-item identity across application retries.
SDK-generated keys protect individual requests but do not make a new app-level
attempt the same item-creation operation.

The required invariant is that retrying a partially successful upsert preserves
one intended copy of each item. Check successful-prefix retries and the final
issuing synchronization. Billing performs another upsert before finalization,
which could remove the duplicate; #1 currently fails before that cleanup.
Therefore USD 20 is an observed draft subtotal, not an observed payment.

Provider contract: [idempotent requests](https://docs.stripe.com/api/idempotent_requests).

## #6: A successful discount update returns the gross line's identity

**Regression:** [discount_monetary_audit_test.go](../test/app/stripe/discount_monetary_audit_test.go),
`TestStripeInvoicing/TestMonetaryAuditDiscountIdentitySurvivesUpdate`.

Initial synchronization correctly creates separate USD 100 gross and USD -40
discount items. In [updateInvoice](../openmeter/app/stripe/appinvoice.go),
`AddLineDiscountExternalID(discount.ID, line.ExternalIDs.Invoicing)` returns the
parent gross line's provider ID for the discount. `MergeIntoInvoice` then
copies that incorrect association into the invoice snapshot. A third sync
maps both USD 100 and USD -40 to the same provider target.

The test assumes a successful second update at the client mock boundary, then
captures the third update plan and returns a sentinel before execution. It
does not teach the HTTP transport to accept the invalid IDs from #1, and it
does not demonstrate completed incorrect collection.

The update result must retain the matched discount line's identity. Verify
that merging a successful result preserves distinct gross and discount
associations through subsequent syncs, including unchanged invoice retries.

## #7: A credit realization split across details maps to one item

**Regression:** [credits_monetary_audit_test.go](../test/app/stripe/credits_monetary_audit_test.go),
`TestStripeInvoicing/TestMonetaryAuditSplitCreditPreservesDistinctProviderItems`.

This is a charges-to-Stripe scenario. Five units at USD 1 plus five at USD 2
produce USD 15 gross. One purchased-credit realization covers USD 5 of the
first detail and USD 2 of the second, leaving USD 8 cash due. Native billing
sanity checks pass, and initial provider synchronization correctly creates two
credit items totaling USD 7.

[WithCreditsApplied](../openmeter/billing/models/stddetailedline/model.go)
intentionally distributes the same realization ID across covered details.
[updateInvoice](../openmeter/app/stripe/appinvoice.go) indexes provider credit
items solely by that ID, so one overwrites the other in the map. Both update
requests target the same item, and the unselected item remains scheduled for
removal. One surviving item cannot represent both deductions.

The test captures the update plan before provider mutation. It proves the
identity collision, not a completed overcharge. A fix must preserve distinct
allocation identities, or aggregate them without losing value or tax treatment.
After #1 is addressed, verify that update, cleanup, and finalization preserve
the full USD 7 deduction and USD 8 cash amount.

Provider contract: [invoice-item amounts and deductions](https://docs.stripe.com/api/invoiceitems/create?api-version=2024-06-20).

## Reproduction and follow-up

Validated on 2026-10-27 against base `9b1736df5373e78476970e459fd2c18fe4372558`:
**9 scenarios: 7 expected regression failures, 2 passing currency controls
(USD and JPY), 0 skipped.** Scoped fast lint and `go vet` pass.

From the repository root, with the development environment and local PostgreSQL:

```sh
direnv exec . env POSTGRES_HOST=127.0.0.1 go test -tags=dynamic -p 8 -count=1 ./test/app/stripe \
  -run '(TestStripeInvoicing|TestStripeFinalizationMonetaryAudit)/(TestMonetaryAudit.*|TestApprovalPreservesProviderTotalAndReachesFinalization)'
```

The shared local provider transport lives in `invoice_monetary_audit_test.go`;
keep it when running the other candidate tests. Tests replace and restore the
Stripe SDK's global HTTP client and must not run in parallel within the package.

Address #1 before claiming end-to-end monetary outcomes for #5, #6, or #7.
After correcting the mappings, rerun approval through finalization and verify
provider totals, orphan cleanup, and retry behavior together. #2 can be
investigated independently. Existing test assertions describe the desired
behavior and are intentionally failing until the corresponding defects are fixed.
